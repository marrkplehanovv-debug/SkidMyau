## 0. TL;DR

Нужно сделать три вещи:

1. **Обучаемая модель следующего тик-дельты yaw/pitch** (порт идеи `AiAngleSmooth` +
   `CombatSample` из LiquidBounce, но без Kotlin/DJL/1.21 — чистый Java 8 + офлайн
   обучение на Python). Модель предсказывает не «куда смотреть», а **насколько
   повернуться за следующий тик**, по предыдущей скорости поворота и геометрии цели.
2. **Перенос той же ротации на блоки** (Scaffold/tower/place) + управляемое
   отклонение точки прицеливания от центра грани (не uniform-random, а обученное
   распределение + медленный дрейф).
3. **Симуляция человечных кликов**: butterfly / double-click / drag-click, CPS-система
   с рандомизацией, устойчивая к *статическому* анализу Polar.

Ключевая мысль, которую нельзя терять:

> Джиттер, сигмовидная траектория и случайная точка наводки — это **стационарный
> низкоразмерный шум**, который ML-античит отделяет от человека почти идеально.
> Работает только **воспроизведение распределения человеческих траекторий**
> (обученная модель + стохастичность + человеческие тайминги и корреляции).

Гарантий обхода нет. Это уменьшение вероятности детекта, а не невидимость.

## 1. Модель угроз и честные ограничения

### 1.1 Что видит облачная ML-проверка Polar/Ersa

Античиты не «ищут паттерн бота» вручную. Они собирают по сессии вектор признаков
(эмбеддинг) из сырого потока пакетов и сравнивают его с распределением людей.
Типичные входы такого классификатора:

**Ротация**
- ряд `Δyaw`, `Δpitch` по тикам (20 Гц), его производные: скорость, ускорение, jerk;
- автокорреляция `Δyaw` на лагах 1..20; спектр (FFT): у бота есть пик на частоте
  сглаживания, у человека спектр близок к 1/f;
- энтропия / sample entropy / Hurst exponent;
- симметрия и кросс-корреляция yaw↔pitch;
- «остановки»: человек почти никогда не держит ровно 0.000° много тиков подряд;
- квантование: остаток `Δ mod step(sensitivity)` — у мыши он нулевой, у silent-ротации
  и у наивного сглаживания — нет;
- «идеальная сходимость»: отсутствие перерегулирования (overshoot) и корректирующих
  микродвижений после быстрого флика;
- реакция на события: hurt/knockback, появление цели, смена цели — у человека есть
  задержка 100–300 мс и провал точности, у бота — мгновенный идеальный трекинг;
- связь прицела с движением: удар всегда точно в момент, когда прицел на цели;
  у человека есть промахи и клики «на упреждение».

**Клики**
- гистограмма интервалов (в 1.8.9 сервер видит клики только на границах тиков,
  т.е. кратно 50 мс — важна гистограмма tick-gaps, а не микросекунды);
- CPS и его дисперсия, автокорреляция интервалов, «усталость» (дрейф CPS);
- периодичность: постоянные 100 мс = бот;
- корреляция клика с прицелом и с движением цели;
- аномальные серии (20 CPS ровно 10 секунд);
- лишние swing/attack пакеты внутри одного тика (в ваниле невозможно).

**Движение/контекст**
- стрейф, спринт, прыжки, GCD-паттерны, «идеальные» углы;
- одновременность действий (бьёт, ест, ставит блок, смотрит в другую сторону).

### 1.2 Почему «джиттер + сигмоида + рандомная точка» не работает

| Приём | Почему палится |
|---|---|
| Гауссов шум на `Δyaw` | шум стационарный и аддитивный → высокая автокорреляция/спектр отличаются от человека; при усреднении по 200 тикам шум исчезает, остаётся идеальная экспонента |
| Сигмоида/экспонента к цели | детерминированная функция состояния: одинаковый вход → одинаковый выход; нет overshoot, нет коррекций, нет латентности |
| Случайная точка на грани | равномерное распределение попаданий; человек кластеризуется ближе к центру/удобной стороне и дрейфует, а не пересэмплирует каждый тик |
| Рандомный CPS из `[min,max]` | равномерное распределение интервалов; у человека гамма-подобное с автокорреляцией и паузами |
| «Человечная» задержка 150 мс константой | константа = признак; нужна случайная величина с хвостом |

### 1.3 Что реально даёт шанс

1. Модель, обученная на **настоящих человеческих траекториях** (не на синтетике).
2. Выход модели — **следующая дельта за тик**, а не абсолютный угол: это сохраняет
   инерцию, ускорение и «почерк» человека.
3. **Стохастичность на входе и на выходе** (heteroscedastic output), а не косметический шум.
4. Явные человеческие тайминги: латентность реакции, overshoot, провал точности
   после урона, паузы.
5. Клики, смоделированные как **процесс во времени**, связанный с прицелом.
6. Офлайн-валидатор, который сам пытается отличить наши траектории от человеческих.
   Критерий приёмки — близкий к случайному AUC.

### 3.2 Поток данных за один тик

```
UpdateEvent(PRE)
  ├─ модули (Scaffold/KillAura/...) выбирают цель и точку прицела
  ├─ RotationPredictor.predict(targetYaw, targetPitch)  [priority 1..3]
  │    ├─ фичи из текущего состояния + истории (ring buffer 32 тика)
  │    ├─ forward -> [dYaw, dPitch]
  │    ├─ stochastic sample (σ из выхода) 
  │    ├─ latency / overshoot / post-hurt modifiers
  │    ├─ GCD quantize + residual carry
  │    └─ event.setRotation(curYaw + dYaw, curPitch + dPitch, priority)
  └─ AngleRecorder.onPre(event)   // финализирует предыдущий семпл меткой
POST
  └─ AngleRecorder.onPost(event)  // фиксирует фактически отправленный угол
```

### 3.3 Рендер vs пакет

- Серверу нужна **дискретная дельта за тик** (20 Гц), квантованная под мышь.
- Клиенту для плавности можно интерполировать, но интерполяция **не должна**
  попадать в `C03PacketPlayer`. Сейчас `RotationManager` растягивает дельту, но
  `event.setRotation` задаёт конечное значение на тик — проверить логом пакетов.
- Запрещено отправлять больше одной look-дельты за тик и «досылать» недостающее
  вторым пакетом: у человека один мышиный поток.

## 4. Данные

### 4.1 Принцип

Датасет — это **поток состояний по тикам**, а не набор независимых строк.
Метка для состояния в тике `t` — это фактическая дельта, наблюдённая в тике `t+1`.
Поэтому рекордер хранит ring buffer и финализирует предыдущий снапшот, когда
приходит следующий.

Это ровно логика `DebugCombatTrainerRecorder` + `CombatSample`:
`velocityDelta = current.rotationDeltaTo(next)` — метка; при инференсе в
`AiAngleSmooth` в качестве «предыдущей скорости» подаётся `previous.rotationDeltaTo(current)`.

### 4.2 Формат JSONL

Файл на сессию: `./config/SkidMyau/ai/raw/<sessionId>.jsonl`, одна строка = один тик.

```json
{
  "v": 2,
  "s": "20261103-120000",
  "tick": 1042,
  "yaw": 91.3241, "pitch": 12.5562,
  "pyaw": 90.1120, "ppitch": 11.9980,
  "dyaw": 1.2121, "dpitch": 0.5582,
  "tyaw": 96.4420, "tpitch": 18.2210,
  "dist": 2.83,
  "pmx": 0.0781, "pmy": -0.0784, "pmz": -0.1622,
  "tmx": 0.0, "tmy": 0.0, "tmz": 0.0,
  "onGround": true,
  "hurt": 0,
  "fu": 0.5, "fv": 0.5,
  "faceW": 37.5,
  "tower": false,
  "aimErr": 3.1,
  "vis": true,
  "step": 0.0096,
  "kind": 1,
  "key": 4711,
  "clk": 7,
  "skip": false
}
```

Поля (реализовано в `AiRotation.AiSample`):
- `yaw/pitch` — итоговая ротация этого тика (после всех модулей);
- `pyaw/ppitch` — ротация предыдущего тика;
- `dyaw/dpitch` — метка: дельта `t → t+1`, дописывается постфактум;
  если тик потерян (телепорт/лаг), ставится `"skip": true` и семпл не используется;
- `tyaw/tpitch` — абсолютная цель (центр грани/бокса), до сглаживания;
- `kind` ∈ `0 IDLE | 1 ENTITY | 2 BLOCK | 3 SCAFFOLD` (int, как в `AiTarget`);
- `key` — идентификатор цели (entityId либо hashCode позиции+грани);
- `fu/fv` — координаты точки прицела в локальной системе грани (0..1);
- `faceW` — видимая угловая ширина грани в градусах (для AimPointNet);
- `step` — шаг мыши при текущей sensitivity (см. §8.2);
- `aimErr` — угловое расстояние от текущего взгляда до цели;
- `clk` — тиков с последнего клика AutoClicker/KillAura;
- `pm*` — движение игрока за тик, `tm*` — движение цели.

Почему JSONL, а не бинарь: удобно диффить, читать Python-ом, докачивать.

### 4.3 Сбор боевых семплов (слизни)

Оставляем подход LiquidBounce, но на 1.8.9:

1. Модуль `AiModule` в режиме `Record`.
2. Спавним слизня (или зомби) в 2–3 блоках перед игроком, случайно:
   `±65°` по yaw, `-20..+10°` по pitch, дистанция `2.0..2.9`.
3. Игрок **сам**aim-ит и бьёт; после удара моб удаляется и спавнится новый.
4. Пишем каждый тик до удара.
5. Минимум: **30 минут чистого боя = ~36 000 тиков** на одну сессию.
   Для нормальной модели нужно **10–20 сессий разных дней/настроений** (200k–700k тиков).

Критично: **запись должна идти с выключенными читами ротации** (KillAura rotations=NONE,
Scaffold off, AimAssist off). Иначе модель учится копировать бота.

Если реального человека нет — используйте записи живых игроков (реплеи/сессии),
но не синтетику. Синтетика даст красивую метрику и нулевой эффект против ML.

### 4.4 Сбор семплов для блоков и scaffold

Два независимых набора:

**(а) Человеческая установка блоков.** Игрок вручную строит мост/башню с
включённым рекордером, Scaffold выключен. Пишем:
- целевую грань (`support + facing`), её размеры, расстояние;
- фактическую точку попадания (raytrace от глаз в момент клика) → `fu/fv`;
- `kind=BLOCK|SCAFFOLD|TOWER`, `tower`, `aimErr`;
- клик по ПКМ как событие.

Это даёт и траектории доводки прицела, и распределение точек на грани.

**(б) Дублирование ротации на блоки.** Отдельно проверяем, что модель,
обученная на сущностях, не разваливается на блоках: фичи геометрии общие
(`tyaw/tpitch/dist/step`), отличаются только `kind`, `fu/fv`, `faceW`.
Если данных по блокам мало — сначала используем `kind`-conditioned смещение
выхода (bias), потом дообучаем.

### 4.5 Сбор кликов

`ClickRecorder` пишет реальные ЛКМ/ПКМ человека (AutoClicker выключен):
```json
{"t": 1730000000123, "btn": 0, "down": true, "aimErr": 4.2, "onTarget": false,
 "cps": 9.7, "sincePrev": 87, "kind": "ENTITY"}
```
Нужно 20–40 минут на каждый стиль (обычный, butterfly, double, drag).
Drag click на мыши с высоким polling даёт много событий — сохраняем всё,
но обучаем **эффективные** интервалы (те, что доходят до сервера).

### 4.6 Гигиена датасета

- Split **по сессиям**, не по строкам. Иначе утечка и метрики врут.
- Выкидывать: телепорты, `|Δ| > 90°` за тик (не физично), лаговые тики,
  смерть/респавн, riding.
- Балансировка по `kind`: не должно быть 95% ENTITY.
- Хранить `sessionId` и `playerId`, версию сборщика.
- Контрольная сессия (никогда не в train) — для финальной валидации.

## 5. Модели

### 5.1 AngleNet (главная)

Повторяем архитектуру LiquidBounce, но с расширенными фичами:

```
Linear(in, 128) → BatchNorm → ReLU
Linear(128, 64) → BatchNorm → ReLU
Linear(64, 32)  → BatchNorm → ReLU
Linear(32, out)
```

- `in` = 6 (v1, совместимо с LB) или 26 (v2, рекомендуется).
- `out` = 2 (`Δyaw`, `Δpitch`) для v1;
  **для v2 рекомендуется `out = 4`: `μyaw, μpitch, logσyaw, logσpitch`** —
  стохастичность учится, а не подмешивается.
- Loss: Gaussian NLL для v2 (`0.5*((y-μ)/σ)^2 + logσ`), L2/Huber для v1.
- Никакого dropout на инференсе, никакой BatchNorm-статистики батча:
  статистика фолдится в веса (см. §6.4).

**Фичи v1 (6, как в `CombatSample.fillAsInput`)**

| # | Фича |
|---|---|
| 0 | `Δyaw` до цели / 180 |
| 1 | `Δpitch` до цели / 90 |
| 2 | предыдущая `Δyaw` / 30 |
| 3 | предыдущая `Δpitch` / 20 |
| 4 | `speed = |playerDiff| + |targetDiff|` (гориз.) |
| 5 | `distance` (кв. boxed distance) |

### 5.2 AimPointNet (точка на грани)

Отдельная маленькая сеть, **не на каждый тик**:

```
in 8: [dist/6, faceW/90, (u-0.5)*2, (v-0.5)*2, speed*20, onGround, aimScale, drift]
Linear(8,32) → ReLU → Linear(32,16) → ReLU → Linear(16,4)  // μu, μv, logσu, logσv
```
(`AimOffset.sample`, режим `LEARNED`; u/v — предыдущая точка, чтобы сеть
предсказывала не абсолют, а следующее положение.)
Loss — Gaussian NLL по записанным `fu/fv`.

Поведение:
- при захвате цели сэмплируем `(u,v) ~ N(μ, σ²)`, клип в `[0.12, 0.88]`;
- дальше **не пересэмплируем каждый тик**, а ведём Ornstein–Uhlenbeck дрейф:
  `du = θ(μu - u)dt + σu·dW`, `θ ≈ 1/6 тика⁻¹`, чтобы точка «жила»;
- пересэмпл только при смене цели/грани или раз в 40–120 тиков;
- итоговая точка обязана проходить `rayTrace` по нужной грани, иначе fallback в центр.

Свойства (см. §8.4): `aim-offset-mode` = `CENTER | LEARNED | RANDOM`,
`aim-offset-scale` 0..100, `aim-offset-drift` 0..100, `aim-offset-resample` 10..200 тиков.

Даже в режиме `RANDOM` это **не uniform**: сэмпл из усечённого нормального с σ,
зависящей от дистанции и размера грани.

### 5.3 ClickProcess (не нейросеть)

Клики — низкоразмерный временной процесс. Нейросеть тут переобучается и даёт
неестественные хвосты. Лучше **параметрическая модель + обученные параметры**:

- базовый интервал: Gamma(k, θ), `mean = 1000/CPS`;
- CPS — OU-процесс вокруг цели (усталость/возбуждение), а не i.i.d.;
- полумарковские состояния: `BURST` (серия), `ADJUST` (переприцел, 120–300 мс),
  `PAUSE` (осознанная пауза 200–600 мс);
- double-click: пара с внутренним гэпом 30–70 мс, серия 2–4 пары;
- drag-click: кластеры с гэпом 50–60 мс и «дрожанием» (в 1.8.9 всё равно
  эффективно ≤ 20 CPS, см. §9.1).

Параметры (k, θ, вероятности переходов, распределение пауз) **фитим на записях
человека** и храним в json. Никаких «магических» констант в коде.

### 5.4 Формат `.skm`

Little-endian, версионированный, читается `ByteBuffer.order(LITTLE_ENDIAN)`.

```
offset  type      value
0       char[4]   "SKM1"
4       u32       version = 1
8       u32       inputSize
12      u32       layerCount
16      ...       layers
```

Слой:
```
u32 outSize
u8  activation      // 0 = linear, 1 = relu, 2 = tanh
f32[outSize*inSize] weights   // row-major: out x in
f32[outSize]        bias
```
`inSize` первого слоя = inputSize, далее = предыдущий outSize.

Рядом `angles-v2.json` (пишет `tools/ai/skm.py:write_meta`):
```json
{
  "name": "angles-v2",
  "inputSize": 26,
  "outputSize": 4,
  "features": ["total_yaw", "... 26 имён ..."],
  "hidden": [128, 64, 32],
  "inputMean": [ ... 26 ... ],
  "inputStd":  [ ... 26 ... ],
  "outputScale": [3.12, 2.04, 1.0, 1.0],
  "stochastic": true,
  "note": "outputScale in degrees; sigma = exp(log_sigma) * scale"
}
```
`outputScale[0..1]` — std дельт в градусах: `delta = out[i] * scale[i]`,
`sigma = exp(out[2..3]) * scale[0..1]`. Java обязана проверять
`inputSize`/`outputSize` и падать в bootstrap, а не в краш.

## 6. Обучение (Python)

### 6.1 Окружение

```
python 3.11, torch 2.x (CPU достаточно), numpy, pandas, scikit-learn
```
GPU не обязателен: 500k × 26 — это минуты на CPU.

### 6.2 `dataset.py`

1. Читает все `raw/*.jsonl`, выбрасывает `skip`.

### 6.3 `train_angles.py`

Обязательные проверки:
- `val` loss по **сессиям**, не по строкам;
- отсутствие `NaN`;
- sanity: модель не выдаёт константу (std выхода > 0.3 от std меток);
- сравнение с baseline «предыдущая дельта» (persistence): модель должна быть лучше.

### 6.4 `export_skm.py`

1. `model.eval()`.
2. Фолдинг BatchNorm в предшествующий Linear:
   ```
   s   = gamma / sqrt(var + eps)
   W'  = W * s[:, None]
   b'  = (b - mean) * s + beta
   ```
   (порядок в LB: Linear → BatchNorm, поэтому фолдим в Linear).
3. Удалить BatchNorm-слои, оставить только Linear+ReLU.
4. Записать `.skm` + `.json` (mean/std, outputScale, sha256).
5. **Проверка эквивалентности**: прогнать 1000 случайных входов через torch и через
   эталонную Java-реализацию (или Python-реализацию того же формата); max abs diff < 1e-4.

### 6.5 Замечание про стохастичность

Если выход 4-мерный, на инференсе:
```java
float muYaw = out[0] * scaleYaw;
float sigYaw = exp(clamp(out[2], -4f, 1f)) * scaleYaw;
float dYaw = muYaw + (float)(rng.nextGaussian() * sigYaw * jitterScale);
```
`jitterScale` — свойство 0..100 (0 = детерминированно). σ учится по данным:
там, где человек непредсказуем (быстрый флик), σ большая; у цели — маленькая.
Это принципиально лучше аддитивного шума.

## 8. Интеграция ротации

### 8.1 API

Не ломаем существующее. Добавляем в `RotationManager`:

и в `RotationPredictor`:


Порядок в модулях:
```java

    event.setRotation(curYaw + out[0], curPitch + out[1], 1);
} else {
    event.setRotation(RotationUtil.getRotations(...), 1);
}
```

### 8.2 GCD-квантование (обязательно)

Мышь в 1.8.9 (`MouseHelper`) умножает счётчик на:
```java
float f = mc.gameSettings.mouseSensitivity * 0.6F + 0.2F;
float step = f * f * f * 8.0F * 0.15F;  // градусов на один «тик» мыши
```
Реальный игрок всегда кратен `step` (сумма кратных за тик). Значит:

```java
static float quantizeDelta(float delta, float step, float[] residual) {
    float want = delta + residual[0];
    float q = Math.round(want / step) * step;
    residual[0] = want - q;          // переносим на следующий тик
    return q;
}
```
- Остаток копится, чтобы прицел всё равно сходился.
- Квантовать **и yaw, и pitch**.
- Не квантовать рендер — только отправляемое значение.
- При `step == 0` (sensitivity 0) не квантовать.
- Логировать `|delta/step - round|` — должен быть < 1e-3.

### 8.3 Silent vs visible

- Для ML-проверки «человечности» нужна **видимая** ротация: сервер должен видеть
  тот же yaw, что и направление удара.
- `SILENT` (ротация только в пакете удара, взгляд клиента не меняется) — это
  отдельный сильный признак: сервер видит look-пакет, не совпадающий с движением
  и с предыдущим yaw, либо видит удар под углом, куда игрок «не смотрел».
- Рекомендация: для KillAura использовать режим `LEGIT` (видимая ротация) вместе
  с AI; `SILENT` оставить опцией, но понимать, что ML-часть его не прикрывает.
- `move-fix`/`setPervRotation` не должны создавать рассинхрон: серверный yaw и
  yaw, использованный для движения, обязаны совпадать в тик удара.

### 8.4 Человеческие модификаторы поверх модели

Модель учится на «чистом» трекинге. Добавляем то, чего в слизневых данных нет:

| Модификатор | Реализация | Зачем |
|---|---|---|
| Латентность захвата | при появлении/смене цели: 2–5 тиков «не реагируем», потом первый большой саккад | у человека есть реакция 100–250 мс |
| Overshoot | первый саккад: `delta *= 1.05..1.25`, затем 1–3 тика коррекции | люди перелетают |
| Провал после урона | `hurtTime > 0`: масштаб модели ×0.3..0.7 на 3–8 тиков | человек «теряется» |
| Микротремор у цели | OU-процесс σ≈0.03–0.08°, τ≈300 мс, **только когда `|Δ|<1°`** | бот замирает идеально |
| Смена цели | сброс истории `prevΔ`, новая латентность | иначе модель «несёт» инерцию |
| Idle | без цели — OU-дрейф 0.02–0.1°/тик | полная неподвижность = бот |
| Ограничение скорости | `|Δ| ≤ 35°/тик` (человек physical limit) | телепорт-снапы |

Все параметры — свойства модуля, а не константы.

### 8.5 Блоки / Scaffold / tower

Сейчас `Scaffold`:
- `getTargetPos()` — предсказанная клетка (под игроком / одна впереди);
- `findBlockData()` — опора+грань ровно в эту клетку;
- в `onUpdate` перебирает `placeOffsets` (сетка 16×16) и выбирает точку с
  минимальным угловым отклонением, проходящую `rayTrace`;
- `event.setRotation(bestYaw, bestPitch, 3)`.

Что меняем:
1. Выбор точки → `AimPoint` (LEARNED/центр/умеренный рандом), а не минимум угла.

2. Доводку угла к `bestYaw/bestPitch` делает модель (те же фичи, `kind=SCAFFOLD`,
   `fu/fv`, `faceW`), а не `getRotationsTo`.
3. Обязательный `rayTrace`-валидатор: если выбранная точка не даёт попадание
   в `blockData.facing()`, откат к центру грани (0.5,0.5).
4. `tower`: при подъёме человек смотрит вниз не идеально; текущий код уже

5. **Не менять** `getTargetPos`/`findBlockData`/`place` без необходимости —

6. Для блоков `AimPoint` в локальных координатах грани:

   ```
   NORTH/SOUTH: x∈[0,1], y∈[0,1], z=0/1
   EAST/WEST:   z∈[0,1], y∈[0,1], x=0/1
   UP/DOWN:     x∈[0,1], z∈[0,1], y=1/0
   ```

   Клип `[0.12, 0.88]` от краёв; для узких граней margin больше.
7. `place-delay`/`multiplace` не трогаем: клики по ПКМ — отдельная подсистема (§9).

## 9. Человечные клики

### 9.1 Физика 1.8.9 (важно понять до реализации)

- Ванильный клиент обрабатывает **максимум один удар за тик** (нажатие
  `keyBindAttack` живёт один тик, `clickMouse()` вызывается из тик-цикла).
- Значит **эффективный CPS ≤ 20**, и «drag click 40 CPS» в 1.8.9 не даёт урона:
  лишние пакеты либо игнорируются, либо это отдельные swing-пакеты, которые
  античит видит как аномалию.
- Сервер видит клики только на границах тиков → интервалы кратны 50 мс.
  Поэтому моделировать надо **tick-gaps** (1,2,3,4 тика) и их распределение,
  а не микросекунды.
- `leftClickCounter`/`NoHitDelay` влияют на блоки, не на сущности.

Вывод: честный диапазон 8–19 CPS с пиками до 20; всё выше — чистый риск.

### 9.2 Режимы

| Режим | Как выглядит у человека | Параметры |
|---|---|---|
| `NORMAL` | 8–12 CPS, ровные серии, редкие паузы | Gamma k≈12–20 |
| `BUTTERFLY` | 12–16 CPS, лёгкая неровность, «двойные» всплески | Gamma k≈6–10 + burst |
| `DOUBLE_CLICK` | пары 30–70 мс, серия 2–4 пары, потом пауза 150–400 мс | пары + пауза |
| `DRAG_CLICK` | кластеры 50–60 мс, до 18–20 CPS, «дрожание», быстро устаёт | Gamma k≈3–6 + дрейф CPS вниз |

### 9.3 Распределение и состояния

Не `nextLong(minCPS, maxCPS)` как сейчас. Вместо этого:

```java
// цель по CPS — OU-процесс (медленный дрейф + усталость)
cps += theta * (cpsTarget - cps) + sigma * gauss();
// интервал — Gamma(k, 1000/cps), затем округление до тиков
double ms = gammaSample(k, 1000.0 / cps);
int ticks = Math.max(1, (int)Math.ceil(ms / 50.0));
```
- `cpsTarget` сэмплируется на «энгейджмент» из `N(μ, σ)`, μ зависит от режима.
- `ticks` — не константа: при 12 CPS это смесь 1 и 2 тиков (50/100 мс).
- Каждые 5–20 секунд — «пауза на переприцел» 3–8 тиков.
- 2–5% кликов «промах» (клик при `aimErr > 8°`), если цель в зоне досягаемости.
- 8% нажатий удерживаются 2 тика (человек не отпускает мгновенно).

### 9.4 Связь с прицелом (главный сигнал античита)

Клик разрешён только если:
```
aimErr < errThreshold(engagement)  &&  modelConverging  &&  !reactionDelay
```
- `errThreshold` сэмплируется 3–7° (у человека не идеально).
- `reactionDelay` — 2–5 тиков после появления цели/после промаха.
- Во время большого флика (`|Δyaw| > 20°/тик`) клики запрещены: человек не бьёт
  в середине разворота, а бот «прилипает».
- После промаха — 2–4 тика паузы (человек переоценивает).
- Не кликать, если `hurtTime > 0` у игрока (пост-хит дезориентация) — опционально.

### 9.5 Реализация в `AutoClicker`

Не переписывать модуль целиком:
1. Добавить `ModeProperty clickMode` (`OFF/NORMAL/BUTTERFLY/DOUBLE/DRAG`).
2. `ClickProcess` отдаёт `boolean shouldClickThisTick(...)` и `int holdTicks`.
3. Заменить `getNextClickDelay()` на `process.nextDelayTicks()`.
4. Оставить `KeyBindUtil.pressKeyOnce` / `setKeyBindState` — это уже корректный
   путь через ванильный `clickMouse`.
5. Не отправлять дополнительные attack-пакеты вручную.
6. Для ПКМ (Scaffold) — тот же процесс с отдельными параметрами (CPS 3–6),
   иначе мост «строчится» нечеловечески.

### 9.6 Свойства (пример)

```java

minCPS/maxCPS      = IntProperty 1..20          // уже были, используются как цель
```

## 10. Валидация против ML-античита

### 10.1 Свой офлайн-детектор (обязательный этап)

`tools/ai/validate.py` обучает классификатор «человек vs сгенерировано» на окнах
20–40 тиков. Признаки окна:

- статистика `Δyaw, Δpitch`: mean, std, skew, kurtosis, min/max;
- `|Δ|` mean/std, доля нулевых тиков;
- автокорреляция лагов 1,2,3,5,10;
- спектральная плотность: доля энергии в 0–2 Гц, 2–5 Гц, >5 Гц; spectral flatness;
- sample entropy, Hurst;
- кросс-корреляция yaw/pitch на лагах 0..5;
- остаток GCD (`Δ mod step`): mean abs, доля «идеальных»;
- overshoot: наличие смены знака `Δ` в пределах 3 тиков после пика;
- «время до цели» и его дисперсия;
- клики: гистограмма tick-gaps, автокорреляция, CPS drift, корреляция с `aimErr`.

Обучение: gradient boosting / logistic regression на **сессиях**.
Оценка: ROC-AUC на held-out сессиях.

**Критерий приёмки: AUC ≤ 0.60** (идеал 0.5–0.55). Если выше — модель/тайминги
слишком «гладкие», возвращаемся к данным и модификаторам.

### 10.2 Метрики модели

- MAE `Δyaw`/`Δpitch` на holdout (цель: < 0.5° при малых дельтах);
- KS-расстояние по распределению `|Δ|` между генерацией и человеком < 0.05;
- доля «идеально нулевых» тиков у цели близка к человеческой (не 90%);
- сходимость: 95% захватов из флика 60° достигают `<1°` за ≤ 8 тиков;
- отсутствие oscillation: число смен знака `Δ` у цели не больше человеческого p95;
- latency-распределение: 2–5 тиков, с хвостом до 8.

### 10.3 Тесты в игре

1. **Packet log**: 200 тиков — квантование, один look-пакет, нет NaN.
2. **Replay**: прогнать записанную человеческую сессию через модель и сравнить
   траектории визуально/метрически (`replay.py` может рисовать графики).
3. **Scaffold**: мост/башня/keep-y не деградировали (сравнить с текущим поведением).
4. **KillAura**: попадания не просели, нет «залипания» на цели.
5. **Клики**: за 60 с CPS в пределах цели ±1, нет интервалов < 50 мс (серверных),
   нет одинаковых подряд идущих интервалов.
6. **Долгий тест 20–30 мин**: нет утечек, модель не грузит CPU (профилировать).

## 12. Риски и чего НЕ делать

1. **Не обучать на синтетике и не обучать на записях с включённым читом** —
   получим самообучение бота.
2. **Не добавлять белый шум на выход** как основной механизм — это первое, что
   ловит ML.
3. **Не пересэмплировать точку прицела каждый тик** — дёрганый hitVec и признак бота.
4. **Не отправлять >1 атаки за тик** и не «дорисовывать» CPS.
5. **Не ломать текущий Scaffold**: пользователь только что стабилизировал
   плейсмент (лишние блоки, keep-y, tower). Любая правка `place/getTargetPos`
   должна быть отдельным PR с регресс-тестом.
6. **Не включать AI по умолчанию**: свойство `ai-rotation` = OFF по умолчанию,
   чтобы откат был в один клик.
7. **Не забывать про другие сигналы**: reach, velocity, hitbox, nofall, blink.
   ML-ротация не прикрывает явные читы; их надо выключать на проверяемых серверах.
8. **Не давать гарантий**: облачная модель переобучается, у Polar/Ersa есть
   серверные корреляции, которых нет в наших данных.
